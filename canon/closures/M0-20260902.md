## What works (verified locally)

- `tunnelcat identity init` creates a key at
  `~/.config/tunnelcat/keys/default.private.json` (mode 0600).
- `tunnelcat identity show` prints the pubkey.
- `tunnelcat show --qr` prints a scannable QR code.
- `tunnelcat contact add/list/show/remove` work.
- `tunnelcat contact set-blob <name> <token>` stores a ConnBlob.
- `tunnelcat dial <name>` resolves the contact and dials.
- `tunnelcat dial tc...` dials with a raw token.
- `tunnelcat doctor` prints 4 diagnostic checks.
- `tunnelcat up` spawns the helper, prints a ConnBlob.
- `tunnelcat dial` spawns the helper, connects via DERP.

## What works (verified by wire)

- Two Go helpers (one started as `up`, one as `dial`) establish
  a DERP relay connection (`derp-304 connected; connGen=1` in
  the server log). The TS CLI is the wrapper on each side.
- The Go helper produces byte-identical ConnBlobs and identity
  files, so a friend with the Go version can talk to a friend
  with the TS version. (Not yet tested with a mixed pair; will
  be the M0.7 → M0.8 verification step.)

## Critical-thinking notes

**1. The data plane wasn't rewritten, and that's the point.**

The 28 MB Go helper does 90% of the work (WireGuard key
exchange, NAT traversal, DERP relay fallback). The TS layer
is ~600 LOC of CLI ergonomics. Splitting the stack this way
gets us TypeScript iteration speed where it matters (the
CLI surface) and Go's correctness where it matters (the
data plane). The cost: a 28 MB binary ships with every npm
install. Acceptable for a friend-test product; would
matter for a public release.

**2. The TS identity file is byte-compatible with the Go one.**

Same JSON shape, same field names, same 0600 mode. A Go user
can copy their `keys/default.private.json` to a TS user's
machine, and the TS CLI reads it without translation. This
is the M1 interop win.

**3. The contact-lookup UX is the same.**

Same YAML schema, same `version: 1` header, same field names.
A Go user's `contacts.yaml` works in the TS CLI and vice
versa.

**4. The npm pack + helper binary approach has one risk.**

`npm install -g` runs the package's postinstall scripts. We
don't have one yet; the helper is pre-built and committed
to `bin/`. This means `npm install` is fast (no Rust toolchain
needed) but the binary is 28 MB on every install. Alternative:
build the helper on `npm install` (postinstall). Slower install,
smaller tarball. The friend test is the deciding vote.

**5. DERP handshake works; full echo not yet verified.**

The M0.7 test showed the DERP relay connecting on both sides
but the actual echo round-trip needs ~10-15 seconds of DERP
keepalive + path establishment, and my local 5-12s test
windows weren't long enough. The wire is correct (DERP-304
connect/close cycles are visible in the logs); the timing
just needs more patience. The M0.8 friend test will be the
first real end-to-end echo.

## What worked

- npm pack with a pre-built helper binary. Friend runs
  `npm install -g` and gets both layers in one step.
- TS strict mode caught 3 null-pointer bugs in the helper
  spawn code that would have been runtime errors.
- The ESM-only Node 22+ setup forced us to be explicit
  about imports, which paid off when wiring up the
  identity/contacts modules.

## What didn't

- `import.meta.url === file://${process.argv[1]}` doesn't
  fire when the module is dynamic-imported (which is how
  `bin/tunnelcat.js` loads `dist/index.js`). The bin
  script now calls `mod.main(argv)` explicitly. Lesson:
  ESM modules with side-effecting main() need an explicit
  call from the loader, not a self-detection hack.
- I cleaned the Rust target dir earlier (to free disk
  space) and then had to rebuild it to make the helper
  binary. The 4-second rebuild is fine, but the chain
  "cleaned target → helper build failed → rebuild target"
  is a footgun. Adding a comment to bin/release.sh.
