# M0 plan — "tunnelcat, in TypeScript, ships fast"

> **Date:** 2026-09-02
> **Status:** planning, not yet started
> **Goal:** same M0 gate as the Go version (1-line install,
> real echo test between two machines), but in a stack that
> iterates faster.
> **Closure doc (when done):** `canon/closures/M0-<date>.md`

## Why a new repo, new stack, same goal

The Go+Rust version (github.com/0ArchLinux0/tunnelcat) has
15/17 M1 sub-steps shipped. The friend test (M1.17) is the
real gate. The user has parked the Rust work and asked for
the same product, same goal, in a stack that gets the
product out faster.

The bottleneck in the Go version is **CLI ergonomics and
distribution friction**, not the data plane. The data plane
(`github.com/tailscale/tailcat` + tailscale.com Go libs) is
correct and works. So we keep the data plane and rewrite
the CLI/distribution.

## Stack

| Layer | Choice | Why |
|---|---|---|
| CLI | TypeScript on Node 22+ | QR codes via `qrcode`, fs via `node:fs`, no compile step, fast iterate |
| Data plane | Go binary (vendored as npm optionalDep) | Correct, working, the only thing that does NAT traversal right |
| Distribution | npm (`@scope/tunnelcat`) | `npx tunnelcat up` — friend doesn't compile anything |
| Wire compat | Byte-compatible with the Go version | Go friend ↔ TS friend interop |
| Identity file | Same JSON shape | `~/.config/tunnelcat/keys/<name>.json` |
| Contacts file | Same YAML shape | `~/.config/tunnelcat/contacts.yaml` |

## Critical-thinking notes (read before starting)

**Note 1: the data plane is the hard part, and we're reusing it.**

The 10% of the Go project that's actually hard (WireGuard key
exchange, NAT traversal, DERP relay fallback) is upstream code.
We bundle it. The 90% that's CLI ergonomics is what we're
rewriting in TypeScript. Don't accidentally try to reimplement
the data plane in TS.

**Note 2: interop is the test.**

If the TS CLI can talk to a Go server, the wire format is
right. Set this up as the M0.3 test: TS dials a Go server,
echo round-trip works.

**Note 3: npm optional deps.**

The Go binary ships as an npm optionalDependency per platform:
```
"optionalDependencies": {
  "@scope/tunnelcat-helper-darwin-arm64": "0.1.0",
  "@scope/tunnelcat-helper-darwin-x64":   "0.1.0",
  "@scope/tunnelcat-helper-linux-x64":    "0.1.0",
  "@scope/tunnelcat-helper-linux-arm64":  "0.1.0"
}
```
At install time, only the right one is downloaded. The TS CLI
finds the binary at `node_modules/@scope/tunnelcat-helper-<plat>/bin/tunnelcat-helper`.

**Note 4: subprocess model.**

The Go helper is a long-running process. The TS CLI spawns it
when `up` or `dial` runs, and pipes stdin/stdout to it. The
helper speaks the same wire protocol on stdout as the Go
`tailcat` library produces. This is the boundary.

**Note 5: don't reach for too much.**

No TS framework (no Nest, no Hono, no oclif). Just `commander`
or hand-rolled argv parsing. No ORM, no DB, no logger library.
stdlib + 3-4 npm deps max.

✓ using helper binary v0.1.0
✓ generated identity (pubkey nodekey:abc...)
🐈 Server listening with new address: tc...long-string...

```sh
# On machine B
$ npx @scope/tunnelcat dial tc...long-string...

hello

That's it. No `git clone`, no `go install`, no Rust toolchain.

## Risks

- **npm install time.** First install downloads ~30 MB of
  optional-dep + npm registry roundtrip. Mitigation: cache the
  helper binary in a known location and check it before
  re-downloading.
- **Helper binary architecture.** M-series Macs need arm64,
  Intel Macs need amd64. Detect at install via `optionalDependencies`.
- **Wire interop.** The Go helper is the same binary the Go
  CLI uses, so the wire format is identical by construction.
  M0.7 tests this.

## Order of work

```
M0.1 (skeleton) ─┬─ M0.3 (identity file)
                 ├─ M0.4 (contacts file)
                 ├─ M0.5 (QR code)
                 └─ M0.2 (CLI dispatches up/dial) ── M0.6 (helper) ── M0.7 (interop) ── M0.8 (1-line install)

Sub-steps M0.3, M0.4, M0.5 are independent of M0.6 (helper

## What I want you to look at, critically

1. **The stack choice.** TypeScript-on-Node for the CLI is
   fast to iterate, but it's not the only choice. Python with
   pipx would also work and is faster to install on systems
   that already have Python. Tell me if you want to switch.
2. **The vendoring model.** npm optionalDependencies works
   but adds 3 platform-specific packages. Alternative: a
   single `@scope/tunnelcat-helper` package with a postinstall
   step that downloads the right binary from GitHub Releases.
   Cleaner. Tell me if you want that.
3. **The 8-step count.** M0 in the Go version was 8 sub-steps
   too. Could be 5. Could be 12. The number is a function of
   "what can fail and need its own test." M0.6 + M0.7 is
   where the most can fail; the rest is plumbing.
