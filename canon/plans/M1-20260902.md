## Why M1 in TS is faster than M1 in Go

The Go version's M1.1-M1.16 was ~16 sub-steps. Many of them
(the CLI ergonomics) are already done in the TS port because
the TS port is **just the CLI**. The data plane (helper) is
the same binary; we don't rewrite it.

## Test gates (per the project rule)

Each M1 sub-step is DONE only when its gate test passes.

### M1.9 gate

`./test/allow.test.ts` — when `up --allow=alice` is given,
the helper is invoked with the correct pubkey (looked up
from contacts). The test mocks `startHelper` to capture
the helper args and asserts the pubkey is in the args.

### M1.13 gate

`.github/workflows/ci.yml` builds the helper for
darwin/arm64, darwin/amd64, linux/amd64, linux/arm64. Each
build's binary is uploaded as an artifact. The CI is
considered green if all 4 builds succeed AND the M0.7 wire
interop test passes against the built helper.

### M1.14 gate

`.github/workflows/release.yml` triggers on `v*` tag push.
The workflow runs the test suite, builds the npm pack, and
uploads the pack as a release artifact. Pass = tag push
produces a usable .tgz.

### M1.15 gate

`./test/loglevel.test.ts` — when `up --log-level=info` is
given, the helper is invoked with `--log-level=info`.

### M1.16 gate

`./test/doctor-derp.test.ts` — doctor check #5 starts a
local TCP server, points the DERP check at it, asserts
"✓" output. With a closed port, asserts "✗" output.
